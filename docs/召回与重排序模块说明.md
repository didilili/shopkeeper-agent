# 召回与重排序模块说明

## 1. 改造目标

问数 Agent 在生成 SQL 前，需要从元数据知识库中找到与用户问题相关的字段、指标和字段取值。原始实现可以完成基础检索，但存在四个工程问题：

1. 多个关键词逐个等待 Embedding 和检索，请求耗时随关键词数量线性增长。
2. 仓储层只返回业务对象，Qdrant 和 Elasticsearch 的原始分数被丢弃。
3. 使用集合去重会破坏查询词顺序，相同输入不易获得稳定、可解释的结果。
4. 同一候选被多个查询词命中时只保留第一次结果，没有融合多路召回证据。

本次改造把这些职责收敛到独立的 `app/retrieval` 模块，并保持 LangGraph 状态结构不变，避免召回算法升级影响后续 Prompt 和 SQL 节点。

## 2. 新召回链路

```text
用户问题与扩展词
    -> 保序去重
    -> 截断异常膨胀的扩展词
    -> 批量生成向量（字段、指标）
    -> 受限并发查询 Qdrant / Elasticsearch
    -> 单个子查询失败时保留其余可用结果
    -> 保留业务对象与原始检索分数
    -> 按业务主键合并重复候选
    -> RRF 多路融合 + 精确名称/别名加分
    -> 稳定排序与 Top-K 截断
    -> 写回 LangGraph 状态
```

字段和指标使用向量召回，字段取值使用全文召回。三条链路共用相同的去重、并发和融合框架，差异由配置与仓储实现承担。

## 3. 核心设计

### 3.1 保序去重

查询词使用首次出现顺序去重。这样既避免重复请求，也不会像 `set` 一样改变顺序，便于复现问题和编写稳定测试。

### 3.2 批量 Embedding 与受限并发

字段和指标的全部查询词统一交给一次客户端调用；客户端再按配置的批大小调用
Embedding 服务，随后并发访问 Qdrant。`asyncio.Semaphore` 控制最大检索并发，
避免关键词较多时压垮下游服务。

LLM 生成的扩展词会在保序去重后按 `max_queries` 截断，防止异常输出把一次
用户请求放大为过多下游查询。Embedding 服务返回的向量数量必须与查询词
数量一致，否则会立即抛出领域异常，避免 `zip` 静默丢失查询。

### 3.3 部分失败降级

多查询召回使用隔离的子任务。单个查询因临时网络问题失败时，服务会记录
查询词、异常类型和错误信息，并继续融合其他成功结果；只有全部子查询都
失败时才抛出 `RetrievalError`，避免把基础设施整体故障误判为“没有候选”。

### 3.4 分数透传

仓储层统一返回 `SearchHit[T]`：

- `item`：字段、指标或字段取值对象。
- `score`：Qdrant 相似度或 Elasticsearch `_score`。

原始分数主要用于阈值过滤、并列候选判定和日志诊断。不同检索引擎的分数尺度不一致，因此不会直接把向量分数与全文分数相加。

### 3.5 RRF 融合

多查询结果使用 Reciprocal Rank Fusion（RRF）融合：

```text
RRF(candidate) = sum(1 / (rrf_k + rank_i))
```

一个候选被多个查询词命中时会累计得分。该方法主要依赖每路结果的名次，对不同查询的分数尺度更稳健。候选名称或别名与查询词完全一致时，再增加可配置的精确匹配加分。

最终排序依次参考：

1. 融合分数；
2. 最佳命中名次；
3. 最高底层检索分数；
4. 稳定业务标识。

最后一项保证完全并列时仍能得到确定性结果。

## 4. 配置与调参

公共默认值位于 `config/app_config.yaml`：

```yaml
retrieval:
  max_concurrency: 8
  max_queries: 12
  column:
    score_threshold: 0.6
    per_query_limit: 20
    final_limit: 20
    rrf_k: 60
    exact_match_boost: 0.05
  metric:
    score_threshold: 0.6
    per_query_limit: 20
    final_limit: 10
    rrf_k: 60
    exact_match_boost: 0.05
  value:
    score_threshold: 0.6
    per_query_limit: 20
    final_limit: 20
    rrf_k: 60
    exact_match_boost: 0.05
```

生产环境优先通过 `.env` 或部署平台环境变量覆盖，例如：

```text
RETRIEVAL_MAX_CONCURRENCY=8
RETRIEVAL_MAX_QUERIES=12
COLUMN_RETRIEVAL_SCORE_THRESHOLD=0.6
COLUMN_RETRIEVAL_FINAL_LIMIT=20
```

建议按以下顺序调参：

1. 用评测问题记录正确字段、指标和值域是否进入候选集，先优化召回率。
2. 调整 `score_threshold` 和 `per_query_limit`，控制单路候选质量与数量。
3. 调整 `final_limit`，平衡 Prompt 上下文完整度、Token 成本和噪声。
4. 只有多查询融合区分度不足时再调整 `rrf_k`。
5. 精确业务术语排名不够靠前时，小幅调整 `exact_match_boost`。
6. 最后根据下游服务容量和 P95 延迟调整 `max_concurrency`。
7. 根据 Prompt 扩展词质量和下游容量调整 `max_queries`，通常不应无限放大。

不要只以“SQL 最终是否执行成功”判断召回质量，否则很难区分检索错误、Prompt 错误和 SQL 生成错误。

## 5. 自动化验证

本模块覆盖以下测试：

- 多查询重复候选能够通过 RRF 排到前面。
- 名称或别名精确命中能够获得加分。
- 完全并列时排序稳定，且正确执行最终 Top-K 截断。
- 查询词保序去重。
- Embedding 使用统一批处理客户端，并按配置拆分请求。
- 检索并发真实生效，并受最大并发限制。
- 单个子查询失败时保留其余结果，全部失败时返回明确的领域异常。
- 扩展词数量上限与 Embedding 响应数量契约。
- Qdrant 与 Elasticsearch 仓储正确透传阈值、条数和原始分数。
- 召回评测集结构、排名指标计算和质量门禁判断正确。

运行全部检查：

```bash
uv run pytest -q
uv run ruff check app tests
uv run ruff format --check app tests
```

## 6. 召回效果评测

`resources/evals/retrieval_cases.yaml` 提供第一版小型黄金评测集，覆盖：

- 6 个字段召回案例；
- 2 个指标召回案例；
- 5 个字段取值召回案例。

字段和指标案例使用业务近义表达，避免全部依赖名称或别名精确匹配；字段值案例使用数仓中的真实枚举值。评测输入是 Prompt 扩展后的检索词，目的是单独衡量检索与融合排序能力，不把 LLM 输出波动混入召回指标。

先在不连接外部服务的情况下校验数据集结构：

```bash
uv run python -m app.scripts.evaluate_retrieval --mode validate
```

Embedding、Qdrant、Elasticsearch 和元数据索引准备完成后运行在线评测：

```bash
uv run python -m app.scripts.evaluate_retrieval --mode live \
  --output reports/retrieval-live.json
```

也可以只评测一个召回域：

```bash
uv run python -m app.scripts.evaluate_retrieval --mode live --domain column
```

报告包含每条案例和各召回域的以下指标：

- `Recall@K`：相关候选进入前 K 名的比例，优先用于判断是否漏召回。
- `MRR@K`：第一个相关候选排名的倒数，衡量正确结果是否足够靠前。
- `nDCG@K`：考虑全部相关候选位置的排序质量。

评测集还声明了最低质量门禁。任意门禁不达标时，在线命令会返回非零退出码，可直接接入 CI。当前门禁是第一版工程目标，不应被当成已经测得的线上基线；首次在线运行后，应保存报告并结合误差案例重新校准。

### 6.1 首次在线基线（2026-07-23）

本次基线使用 MySQL 8.0、Elasticsearch 8.19.10、Qdrant 1.16、TEI CPU 1.8 和 `bge-large-zh-v1.5`，完成元数据知识库重建后运行 13 条在线召回案例。

首次结果为：

- `Recall@1 = 0.9231`
- `MRR@10 = 0.9615`
- `nDCG@10 = 0.9716`
- `Recall@3/5/10 = 1.0000`

误差分析发现，Qdrant 会为同一业务对象的名称、描述、别名分别保存向量点。原融合逻辑把同一检索词返回的重复业务对象多次加入 RRF 分数，导致拥有多个相似向量点的 `order_quantity` 超过正确字段 `order_amount`。

修复后，同一个业务对象在单个检索词中只按首次出现的唯一排名贡献一次 RRF 分数，但仍可在不同检索词之间累积证据。重新运行同一评测集后，全部 13 条案例的 `Recall@K`、`MRR@K` 和 `nDCG@K` 在 K 为 1、3、5、10 时均为 `1.0000`，所有质量门禁通过。

该结果只代表当前小型黄金集的回归基线，不代表生产环境准确率。后续应增加多相关答案、复合问法、错别字、口语表达和困难负例，并保留人工审核，避免针对少量案例过拟合。

## 7. 面试讲解要点

可以按“问题—方案—取舍—验证”说明这次改造：

- 问题：原实现串行调用、丢失分数、结果不稳定，也没有真正融合多关键词证据。
- 方案：抽取通用召回服务，批量 Embedding、受限并发、分数透传、稳定去重，再通过 RRF 融合。
- 取舍：RRF 不直接比较不同检索源的绝对分数，工程上更稳健；暂未引入 Cross-Encoder，避免增加部署资源和在线延迟。
- 验证：通过融合、顺序、并发和仓储契约测试验证，再以黄金评测集计算 Recall@K、MRR@K 和 nDCG@K，并用质量门禁阻止效果回退。

首次在线基线完成后，再根据失败案例决定调整阈值、扩充别名，还是增加 Cross-Encoder 或 LLM reranker。不要在没有误差证据时直接引入更重的重排模型。
