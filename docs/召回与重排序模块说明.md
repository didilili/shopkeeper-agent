# 召回与重排序模块说明

## 1. 改造目标

问数 Agent 在生成 SQL 前，需要从元数据知识库中找到与用户问题相关的字段、指标和字段取值。原始实现可以完成基础检索，但存在四个工程问题：

1. 多个关键词逐个等待 Embedding 和检索，请求耗时随关键词数量线性增长。
2. 仓储层只返回业务对象，Qdrant 和 Elasticsearch 的原始分数被丢弃。
3. 使用集合去重会破坏查询词顺序，相同输入不易获得稳定、可解释的结果。
4. 同一候选被多个查询词命中时只保留第一次结果，没有融合多路召回证据。

本次改造把这些职责收敛到独立的 `app/retrieval` 模块，并保持 LangGraph 状态结构不变，避免召回算法升级影响后续 Prompt 和 SQL 节点。

## 2. 新召回链路

```text
用户问题与扩展词
    -> 保序去重
    -> 批量生成向量（字段、指标）
    -> 受限并发查询 Qdrant / Elasticsearch
    -> 保留业务对象与原始检索分数
    -> 按业务主键合并重复候选
    -> RRF 多路融合 + 精确名称/别名加分
    -> 稳定排序与 Top-K 截断
    -> 写回 LangGraph 状态
```

字段和指标使用向量召回，字段取值使用全文召回。三条链路共用相同的去重、并发和融合框架，差异由配置与仓储实现承担。

## 3. 核心设计

### 3.1 保序去重

查询词使用首次出现顺序去重。这样既避免重复请求，也不会像 `set` 一样改变顺序，便于复现问题和编写稳定测试。

### 3.2 批量 Embedding 与受限并发

字段和指标的全部查询词通过一次批量 Embedding 调用生成向量，然后并发访问 Qdrant。`asyncio.Semaphore` 控制最大并发，避免关键词较多时压垮下游服务。

### 3.3 分数透传

仓储层统一返回 `SearchHit[T]`：

- `item`：字段、指标或字段取值对象。
- `score`：Qdrant 相似度或 Elasticsearch `_score`。

原始分数主要用于阈值过滤、并列候选判定和日志诊断。不同检索引擎的分数尺度不一致，因此不会直接把向量分数与全文分数相加。

### 3.4 RRF 融合

多查询结果使用 Reciprocal Rank Fusion（RRF）融合：

```text
RRF(candidate) = sum(1 / (rrf_k + rank_i))
```

一个候选被多个查询词命中时会累计得分。该方法主要依赖每路结果的名次，对不同查询的分数尺度更稳健。候选名称或别名与查询词完全一致时，再增加可配置的精确匹配加分。

最终排序依次参考：

1. 融合分数；
2. 最佳命中名次；
3. 最高底层检索分数；
4. 稳定业务标识。

最后一项保证完全并列时仍能得到确定性结果。

## 4. 配置与调参

公共默认值位于 `conf/app_config.yaml`：

```yaml
retrieval:
  max_concurrency: 8
  column:
    score_threshold: 0.6
    per_query_limit: 20
    final_limit: 20
    rrf_k: 60
    exact_match_boost: 0.05
  metric:
    score_threshold: 0.6
    per_query_limit: 20
    final_limit: 10
    rrf_k: 60
    exact_match_boost: 0.05
  value:
    score_threshold: 0.6
    per_query_limit: 20
    final_limit: 20
    rrf_k: 60
    exact_match_boost: 0.05
```

生产环境优先通过 `.env` 或部署平台环境变量覆盖，例如：

```text
RETRIEVAL__MAX_CONCURRENCY=8
RETRIEVAL__COLUMN__SCORE_THRESHOLD=0.6
RETRIEVAL__COLUMN__FINAL_LIMIT=20
```

建议按以下顺序调参：

1. 用评测问题记录正确字段、指标和值域是否进入候选集，先优化召回率。
2. 调整 `score_threshold` 和 `per_query_limit`，控制单路候选质量与数量。
3. 调整 `final_limit`，平衡 Prompt 上下文完整度、Token 成本和噪声。
4. 只有多查询融合区分度不足时再调整 `rrf_k`。
5. 精确业务术语排名不够靠前时，小幅调整 `exact_match_boost`。
6. 最后根据下游服务容量和 P95 延迟调整 `max_concurrency`。

不要只以“SQL 最终是否执行成功”判断召回质量，否则很难区分检索错误、Prompt 错误和 SQL 生成错误。

## 5. 自动化验证

本模块覆盖以下测试：

- 多查询重复候选能够通过 RRF 排到前面。
- 名称或别名精确命中能够获得加分。
- 完全并列时排序稳定，且正确执行最终 Top-K 截断。
- 查询词保序去重。
- Embedding 使用一次批量调用。
- 检索并发真实生效，并受最大并发限制。
- Qdrant 与 Elasticsearch 仓储正确透传阈值、条数和原始分数。

运行全部检查：

```bash
uv run pytest -q
uv run ruff check app tests
uv run ruff format --check app tests
```

## 6. 面试讲解要点

可以按“问题—方案—取舍—验证”说明这次改造：

- 问题：原实现串行调用、丢失分数、结果不稳定，也没有真正融合多关键词证据。
- 方案：抽取通用召回服务，批量 Embedding、受限并发、分数透传、稳定去重，再通过 RRF 融合。
- 取舍：RRF 不直接比较不同检索源的绝对分数，工程上更稳健；暂未引入 Cross-Encoder，避免增加部署资源和在线延迟。
- 验证：通过融合、顺序、并发和仓储契约测试验证，并为后续离线召回率、MRR、nDCG 评测保留扩展点。

下一阶段可以建立带标准字段、指标和值域标签的检索评测集，统计 Recall@K、MRR 和 nDCG，再决定是否增加 Cross-Encoder 或 LLM reranker。
